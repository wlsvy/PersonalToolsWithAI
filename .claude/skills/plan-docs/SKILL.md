# 계획 문서: 사람용 / AI용 분리

계획·설계 문서를 쓸 때는 항상 두 파일을 짝으로 만듭니다.

| 파일 | 독자 | 내용 |
|------|------|------|
| `<name>.md` | 사람이 읽습니다. | 무엇을, 왜, 어떤 순서로 하는지 담습니다. 기술 디테일은 거칠게 쳐냅니다. |
| `<name>.ai.md` | AI 에이전트가 읽습니다. | 구현에 필요한 기술 디테일을 모두 담습니다. |

`doc.md`가 이미 있으면 AI용 문서는 같은 위치에 `doc.ai.md`로 둡니다. 한쪽을 고치면 다른 쪽도 함께 맞춥니다.

## 사람용 `<name>.md`
- 한 화면 안팎으로 읽히게 씁니다.
- 담을 것은 목적과 배경, 결정 사항(선택한 것과 짧은 이유), 범위(하는 것과 하지 않는 것), 단계별 순서, 남은 위험과 열린 질문입니다.
- 파일 경로, 함수명, 스키마, 엔드포인트 목록, 라이브러리 버전, 명령어, 코드 조각은 뺍니다. 꼭 필요한 고유명사(예: "Go + SQLite")만 남깁니다.
- 문서 맨 위에 `상세: <name>.ai.md` 링크를 한 줄 넣습니다.

## AI용 `<name>.ai.md`
- 에이전트가 이 문서만 보고 구현할 수 있는 수준으로 씁니다.
- 파일·디렉터리 구조, 의존성, 스키마, API 계약, 핵심 로직의 규칙, 엣지 케이스, 재사용할 기존 코드 경로, 검증 명령, 하지 않을 것을 담습니다.
- 산문보다 목록, 표, 코드 블록을 씁니다.
- 문서 맨 위에 `요약: <name>.md` 링크를 한 줄 넣습니다.

## 파일 분리
문서 하나에 모든 내용을 몰지 않습니다. 피처별, 시스템 레이어별(서버, 앱, 클라이언트 등), 도메인별로 파일을 나눕니다.
- 진입점 문서(`<name>.md` / `<name>.ai.md`)에는 전체 개요와 하위 문서 링크만 둡니다.
- 하위 문서도 사람용/AI용 짝 규칙을 똑같이 따릅니다. 예: `server.md` + `server.ai.md`, `feeds.md` + `feeds.ai.md`
- 나누는 기준은 "따로 바뀌는가"입니다. 함께 바뀌는 내용은 한 파일에 둡니다.

```
docs/
  plan.md / plan.ai.md         개요와 링크
  server.md / server.ai.md     레이어
  app.md / app.ai.md
  feeds.md / feeds.ai.md       도메인/피처
```

## YAGNI와 과적합
필요 없는 기능은 만들지 않습니다. 그렇다고 현재 상태에 과적합해서는 안 됩니다.
- 개발 맥락을 코드에 하드코딩하지 않습니다. 지금의 사용자 수, 환경, 경로, 구현이 한 가지뿐이라는 가정 같은 것들입니다. 이런 값은 설정, 인터페이스 경계, 계층 분리 뒤에 둡니다.
- 기능을 미리 만드는 것(YAGNI 위반)과 나중에 바꿀 수 있는 구조를 남기는 것은 다릅니다. 후자는 지킵니다.
- **확장성에 관련된 결정은 직접 정하지 말고 항상 사용자에게 의견을 묻습니다.** 다중 사용자, 저장소 교체, 플랫폼 추가, 인증 방식, API 버전 관리 같은 것들입니다. 계획 문서에는 "확장성 결정" 섹션을 두고, 열린 질문과 선택지를 적습니다.

## 플랜 모드
플랜 파일(`~/.claude/plans/*.md`) 자체는 승인용이라 하나로 둡니다. 다만 구현을 시작할 때 저장소 안에 이 규칙대로 두 파일을 만듭니다.
